P3 — Controlled Integration and Revision Loop

P3 adds the only permitted path from an independently accepted patch into the authoritative Git repository.

The central rule is:

    Implementation agents and reviewer agents may create, inspect, test, and recommend patches, but they never receive credentials or permissions capable of modifying the authoritative repository.

Only a dedicated Integration Worker, operating after explicit human approval, may create and push a controlled commit.

3. Core invariants

P3 should enforce the following invariants in code and database constraints.
3.1 Patch eligibility

A patch is integration-eligible only when:

patch.status == accepted
review.decision == accepted
review is independent
execution attempt completed successfully
approved work package matches patch work package
patch base commit matches approved execution base commit
patch hash exists
changed-file scope validation passed
required execution tests passed
no unresolved review findings exist

Eligibility must be computed by the server. It must never be accepted directly from an API request.

Do not expose an endpoint such as:

POST /patches/{id}/mark-eligible

Instead, eligibility is derived and persisted after accepted review.
3.2 Human approval

Human integration approval must be separate from:

    requirements approval;

    architecture approval;

    work-package approval;

    patch review;

    patch acceptance.

A reviewer accepting a patch does not authorize repository modification.

The approval record must identify:

    approver identity;

    approver role;

    patch ID;

    exact patch SHA-256;

    target repository;

    target branch;

    expected base commit;

    expected base tree hash;

    approved post-integration test commands;

    approval timestamp;

    approval reason;

    approval policy version.

Changing any protected field invalidates the approval.
3.3 Fresh integration snapshot

The Integration Worker must not reuse:

    the implementation container;

    the implementation snapshot;

    the reviewer snapshot;

    a previous integration working directory;

    an unverified cached Git worktree.

Every integration attempt starts from a fresh clone or fresh trusted mirror checkout.

git clone --no-checkout <authoritative-remote>
git checkout --detach <approved-base-commit>

Then the worker verifies:

HEAD commit == approved base commit
HEAD tree   == approved base tree hash
working tree is clean
no unexpected submodule state
remote URL matches repository policy

3.4 Protected target branch

The target branch should be protected at two levels.
Repository-level protection

Examples:

    no force push;

    no branch deletion;

    required status checks;

    restricted push identity;

    signed commits where supported;

    linear or controlled merge policy;

    no direct developer-agent credentials.

Application-level protection

The Integration Worker must allow only configured branches:

repositories:
  ai-enterprise:
    remote: git@github.com:example/ai-enterprise.git
    integration_target_branches:
      - main
    push_identity: enterprise-integration-bot

A request containing an arbitrary target branch must be rejected.

CREATE TABLE execution_attempt_revision_findings (

Rules:

Initial attempt:
    parent_attempt_id = NULL
    revision_source_review_id = NULL
    lineage_depth = 0
    root_attempt_id = self

Revision attempt:
    parent_attempt_id = immediately preceding attempt
    revision_source_review_id = changes-requested review
    lineage_depth = parent.lineage_depth + 1
    root_attempt_id = parent.root_attempt_id

A revision attempt must never point to an unrelated work package or project.
7. Revision loop

When a reviewer selects changes_requested, the platform should not reopen the existing execution attempt.

It should create a new immutable attempt.

Attempt 1
  ├── Patch 1
  └── Review 1: changes requested
          ├── Finding A
          └── Finding B
                 │
                 ▼
Attempt 2
  parent_attempt_id = Attempt 1
  revision_source_review_id = Review 1
  revision_findings = [A, B]
  ├── Patch 2
  └── Review 2: accepted

Revision execution input

The new implementation runtime receives:

    original approved work package;

    original architectural constraints;

    parent attempt metadata;

    parent patch;

    review findings;

    approved repository base;

    permitted file scope;

    permitted tests;

    revision-specific instructions.

It must not receive permission to expand the work-package scope.

A suitable revision instruction envelope is:

{
  "execution_attempt_id": "uuid",
  "parent_attempt_id": "uuid",
  "work_package_id": "uuid",
  "base_commit_sha": "abc123",
  "review_findings": [
    {
      "finding_id": "uuid",
      "severity": "major",
      "file_path": "app/services/integration.py",
      "description": "Patch does not verify the expected tree hash.",
      "required_change": "Reject integration when the checked-out tree differs."
    }
  ],
  "allowed_paths": [
    "app/services/integration.py",
    "tests/integration/test_integration_service.py"
  ],
  "approved_test_commands": [
    ["pytest", "tests/integration/test_integration_service.py"]
  ]
}

10. Integration Worker algorithm

The Integration Worker should implement this exact sequence.

def execute_integration(attempt_id: UUID) -> None:
    attempt = load_and_lock_attempt(attempt_id)

    verify_attempt_is_queued(attempt)
    mark_verifying(attempt)

    approval = load_approval(attempt.integration_approval_id)
    patch = load_patch(attempt.patch_id)
    eligibility = load_eligibility(patch.id)
    repository = load_repository(attempt.repository_id)

    verify_approval_is_active(approval)
    verify_patch_is_eligible(patch, eligibility)
    verify_approval_matches_patch(approval, patch)
    verify_target_branch_is_allowed(repository, attempt.target_branch)

    with fresh_integration_workspace() as workspace:
        clone_authoritative_repository(repository, workspace)

        verify_remote_identity(workspace, repository)
        fetch_target_branch(workspace, attempt.target_branch)

        checkout_approved_base_commit(
            workspace,
            approval.approved_base_commit_sha,
        )

        actual_commit = read_head_commit(workspace)
        actual_tree = read_head_tree(workspace)

        verify_equal(
            actual_commit,
            approval.approved_base_commit_sha,
            "BASE_COMMIT_MISMATCH",
        )

        verify_equal(
            actual_tree,
            approval.approved_base_tree_sha,
            "BASE_TREE_MISMATCH",
        )

        verify_clean_worktree(workspace)

        patch_bytes = artifact_store.read(patch.artifact_id)
        actual_patch_hash = sha256(patch_bytes)

        verify_equal(
            actual_patch_hash,
            approval.approved_patch_sha256,
            "PATCH_HASH_MISMATCH",
        )

        apply_patch_with_git(workspace, patch_bytes)
        verify_clean_patch_application(workspace)
        verify_changed_paths(workspace, patch.allowed_paths)

        resulting_tree = calculate_candidate_tree(workspace)

        run_approved_tests(
            workspace=workspace,
            commands=approval.approved_test_commands,
        )

        commit_sha = create_controlled_commit(
            workspace=workspace,
            identity=repository.integration_identity,
            message=build_commit_message(attempt, patch),
        )

        verify_commit_parent(
            workspace,
            commit_sha,
            approval.approved_base_commit_sha,
        )

        push_commit(
            workspace=workspace,
            remote=repository.remote,
            target_branch=attempt.target_branch,
            expected_remote_head=approval.approved_base_commit_sha,
        )

        verify_remote_commit(
            repository,
            attempt.target_branch,
            commit_sha,
        )

        record_success(
            attempt=attempt,
            commit_sha=commit_sha,
            resulting_tree=resulting_tree,
        )

11. Preventing race conditions

The authoritative branch may change between approval and integration.

P3 must not silently rebase or apply the patch to a newer base.

Use a lease-style push:

git push \
  --force-with-lease=refs/heads/main:<approved-base-commit> \
  origin \
  HEAD:refs/heads/main

However, because force operations are undesirable on protected branches, the preferred operation is:

git push origin HEAD:refs/heads/main

combined with:

    checkout exact approved base;

    create a commit whose parent is that base;

    branch protection rejects non-fast-forward updates;

    verify the remote head immediately before push;

    fail when the target branch moved.

The failure should be:

TARGET_BRANCH_ADVANCED

The platform then requires:

    a new base snapshot;

    potentially a new execution attempt;

    new review;

    new integration eligibility;

    new human approval.

Do not automatically transplant the accepted patch onto the changed branch.

13. Post-integration tests

There are two test phases.
Execution tests

Run inside the disposable implementation environment before patch review.

Purpose:

    validate implementation behavior;

    verify the work package;

    produce review evidence.

Post-integration tests

Run from the fresh integration snapshot after applying the exact approved patch.

Purpose:

    ensure the patch still applies;

    ensure the approved base is correct;

    verify integration-context behavior;

    detect omitted files or generated artifacts;

Before P3.6: a recommended architectural refinement

At this point, the implementation has accumulated several long-running worker operations. Rather than keeping all runtime state in a single IntegrationAttempt, introduce a finer-grained execution model:

IntegrationAttempt
        │
        ├── Run 1
        │     ├── SnapshotStage
        │     ├── PatchStage
        │     ├── TestStage
        │     ├── CommitStage
        │     └── PushStage
        │
        ├── Run 2 (if infrastructure retry allowed)
        └── ...

This adds an integration_attempt_runs aggregate that records each execution of an attempt separately. The business decision ("integrate this approved patch") remains immutable, while operational retries (worker crash, transient network outage, container restart) become independently auditable.

Benefits include:

    Clear separation between business state and runtime state.

    Safe worker restart after infrastructure failures.

    Detailed timing and resource metrics per run.

    Easier diagnosis of intermittent issues.

    Foundation for future distributed execution across multiple integration workers.

With this refinement in place, P3.6 can focus entirely on rollback metadata, recovery procedures, failure classification, and long-term operational resilience without overloading the IntegrationAttempt aggregate.

P3.6 — Rollback Metadata, Recovery Procedures, and Operational Resilience

P3.6 completes the controlled integration lifecycle.

The objective is not to promise that every integration can be automatically reversed. The objective is to preserve enough verified evidence to:

    determine exactly what changed;

    classify the failure;

    identify whether the authoritative branch changed;

    construct a safe rollback candidate;

    require appropriate human authorization;

    execute recovery without rewriting history;

    preserve the complete incident trail.

The default rollback strategy is:

forward-only recovery through a new revert commit

Never:

force push
reset protected branch
rewrite published history
delete the integration commit
silently alter audit records

1. P3.6 execution model

After successful integration:

Approved patch
      │
      ▼
Controlled commit
      │
      ▼
Restricted push
      │
      ▼
Verified remote commit
      │
      ▼
Integration completed
      │
      ▼
Rollback metadata generated

If a later problem is reported:

Incident detected
      │
      ▼
Create rollback assessment
      │
      ▼
Verify remote repository state
      │
      ▼
Determine recovery strategy
      │
      ├── no rollback required
      │
      ├── revert commit possible
      │
      ├── compensating patch required
      │
      └── manual recovery required
      │
      ▼
Human rollback approval
      │
      ▼
Fresh recovery attempt
      │
      ▼
Tests
      │
      ▼
Controlled recovery commit
      │
      ▼
Restricted push
      │
      ▼
Remote verification

Rollback must be implemented as a new governed workflow, not as a direct administrative Git operation.
2. Core principle: rollback is not deletion

Once the integration commit exists on the protected branch, it is part of the repository history.

The platform must preserve:

base commit
integration commit
candidate tree
remote verification
approval
review
tests
worker run
push evidence

Recovery creates additional history:

Base commit A
      │
      ▼
Integration commit B
      │
      ▼
Rollback or recovery commit C

It must never transform history into:

Base commit A

by deleting commits B and C.

4. When a normal revert is safe

A direct revert commit is usually possible when:

the integration commit exists in protected-branch history
the repository can construct an inverse diff
the revert applies without conflicts
the resulting paths remain within authorized recovery scope
required tests pass
repository policy permits recovery commits

A normal revert may be unsafe or insufficient when the integration changed:

database schemas
external data
message formats
deployed infrastructure
cloud resources
secrets
external APIs
irreversible migrations
published packages
user-generated data

In those cases, the Git revert may be only one component of a larger recovery plan.

9. Why store an inverse diff artifact

A revert can be generated later using:

git revert

However, preserving an inverse diff at integration time provides independent evidence.

It allows the platform to prove:

what the exact inverse of the integrated change was
at the moment integration completed

Generate it from the trusted repository state:

git diff <integration-commit>^ <integration-commit>

The inverse can be represented as:

git diff -R <parent> <integration>

or equivalently:

git diff <integration> <parent>

Store the result as an immutable artifact with SHA-256.

The inverse diff is evidence, not automatic authorization to apply it.

class RollbackMetadataService:
    RECOVERY_POLICY_VERSION = "recovery-v1"

    def build(
        self,
        *,
        repository_path,
        integration_attempt,
        integration_commit,
        approved_test_commands,
    ):
        parent_commit_sha = self._git.run(
            "rev-parse",
            f"{integration_commit.commit_sha}^",
            cwd=repository_path,
        ).stdout.strip()

        parent_tree_sha = self._git.run(
            "rev-parse",
            f"{parent_commit_sha}^{{tree}}",
            cwd=repository_path,
        ).stdout.strip()

        inverse_diff = self._git.run(
            "diff",
            "--binary",
            "--full-index",
            integration_commit.commit_sha,
            parent_commit_sha,
            cwd=repository_path,
        ).stdout.encode("utf-8")

        changed_paths = self._collect_changed_paths(
            repository_path=repository_path,
            parent_commit_sha=parent_commit_sha,
            integration_commit_sha=(
                integration_commit.commit_sha
            ),
        )

        inverse_artifact = self._artifact_store.write_bytes(
            artifact_type="integration_inverse_diff",
            content=inverse_diff,
            media_type="text/x-diff",
        )

        payload = {
            "integration_attempt_id": str(
                integration_attempt.id
            ),
            "integration_commit_sha": (
                integration_commit.commit_sha
            ),
            "parent_commit_sha": parent_commit_sha,
            "integration_tree_sha": (
                integration_commit.tree_sha
            ),
            "parent_tree_sha": parent_tree_sha,
            "changed_paths_sha256": sha256_json(
                changed_paths
            ),
            "inverse_diff_sha256": (
                inverse_artifact.sha256
            ),
            "original_patch_sha256": (
                integration_attempt.expected_patch_sha256
            ),
            "approved_test_commands_sha256": (
                integration_attempt
                .expected_test_commands_sha256
            ),
            "recovery_policy_version": (
                self.RECOVERY_POLICY_VERSION
            ),
        }

        return RollbackMetadata(
            parent_commit_sha=parent_commit_sha,
            parent_tree_sha=parent_tree_sha,

# app/application/policies/recovery_strategy_policy.py

class RecoveryStrategyPolicy:
    POLICY_VERSION = "recovery-assessment-v1"

    def determine(
        self,
        *,
        rollback_record,
        remote_state,
        repository_policy,
    ):
        findings: list[dict] = []

        if not remote_state.integration_commit_is_ancestor:
            findings.append({
                "code": "INTEGRATION_COMMIT_NOT_IN_HISTORY",
                "severity": "critical",
            })

            return RecoveryDecision(
                strategy="manual_recovery",
                risk_level="critical",
                direct_revert_possible=False,
                findings=findings,
            )

        if rollback_record.external_side_effects_declared:
            findings.append({
                "code": "EXTERNAL_SIDE_EFFECTS_DECLARED",
                "severity": "high",
            })

        if rollback_record.database_change_detected:
            findings.append({
                "code": "DATABASE_CHANGE_DETECTED",
                "severity": "high",
            })

        if rollback_record.deployment_change_detected:
            findings.append({
                "code": "DEPLOYMENT_CHANGE_DETECTED",
                "severity": "high",
            })

        if (
            rollback_record.database_change_detected
            or rollback_record.external_side_effects_declared
        ):
            return RecoveryDecision(
                strategy="compensating_patch",
                risk_level="high",
                direct_revert_possible=False,
                findings=findings,
            )

        return RecoveryDecision(
            strategy="revert_commit",
            risk_level="medium",
            direct_revert_possible=True,
            findings=findings,
        )

This policy should be conservative.

False positives are preferable to unsafe automatic rollback.

21. Current remote-state problem

A critical difference exists between integration and rollback.

For integration, the expected target head was the original base commit.

For rollback, other legitimate commits may have been added after the integration commit.

Example:

A — B — C — D
    ↑
 integration commit

The platform must decide whether it is safe to revert B when current head is D.

It must not require:

current head == integration commit

in every case.

Instead it must verify:

integration commit is an ancestor of current head
current head equals the head approved during rollback authorization

This prevents applying the approved recovery against a different branch state.
22. Recovery remote-state policy

class RecoveryRemoteStatePolicy:
    def verify_before_execution(
        self,
        *,
        approval,
        current_remote_head_sha: str,
        integration_commit_is_ancestor: bool,
    ) -> None:
        if (
            current_remote_head_sha
            != approval.expected_remote_head_sha
        ):
            raise RecoveryRemoteStateChanged(
                "The target branch changed after "
                "rollback approval."
            )

        if not integration_commit_is_ancestor:
            raise RecoveryHistoryInvalid(
                "The integration commit is no longer "
                "an ancestor of the protected branch."
            )

If the branch moves after rollback approval:

stop
reassess
obtain new approval

Do not automatically rebase the recovery commit.
23. Creating a fresh recovery snapshot

Recovery must use a new disposable workspace.

Never reuse the original integration workspace.

Flow:

fresh clone
verify remote identity
fetch target branch
verify expected current remote head
checkout current remote head detached
verify tree
verify clean state
verify integration commit ancestry

The recovery commit is based on the current approved branch head, not necessarily the original integration commit.
24. Revert commit creation

For a simple one-parent integration commit:

git revert --no-commit <integration-commit-sha>

Use:

shell=False
hooks disabled
isolated Git configuration
no editor
no signing unless controlled signing is implemented

Recommended environment:

GIT_EDITOR=/bin/false
GIT_SEQUENCE_EDITOR=/bin/false
GIT_TERMINAL_PROMPT=0

Invocation:

git.run(
    "-c",
    "credential.helper=",
    "-c",
    "core.hooksPath=/dev/null",
    "revert",
    "--no-commit",
    "--no-edit",
    integration_commit_sha,
    cwd=repository_path,
)

Because the integration commit is guaranteed to have one parent, -m is not required.
25. Revert conflicts

A later commit may have modified the same lines.

Example:

Integration B changes auth.py
Later commit C also changes auth.py

Then:

git revert --no-commit B

may conflict.

The recovery worker must not resolve the conflict autonomously in P3.6.

It must:

capture conflict paths
abort revert
record evidence
mark REVERT_CONFLICT
require compensating patch workflow

Abort:

git revert --abort

Verify the repository returns to a clean state.
26. Conflict evidence

Persist:

rollback_paths <= original_changed_paths

39. Stage idempotency

Every pipeline stage should have an idempotency rule.

Example:
Snapshot stage

May rerun if no verified snapshot was persisted for the current run.
Patch stage

May not blindly rerun against an unknown workspace.

It requires a fresh verified snapshot.
Test stage

May rerun only against the same verified candidate tree.
Commit stage

If a commit was already created, verify and reuse the exact commit rather than creating a second one.
Push stage

Never repeat merely because the worker did not observe the result.

First query the remote.

If remote already points to the expected commit:

treat push as successful after verification

If remote points elsewhere:

manual intervention

40. Push uncertainty recovery

A classic failure:

worker sends push
remote accepts push
network connection breaks before response

The worker does not know whether push succeeded.

Correct handling:

do not push again immediately
query remote branch

Outcomes:
Remote equals expected commit

push succeeded
continue remote verification

Remote equals old base commit

push likely did not succeed
retry may be allowed according to policy

Remote equals another commit

concurrency conflict
stop
manual assessment

This logic is required for both integration and recovery pushes.
41. Recovery after worker crash
Crash before workspace modification

Safe to start a new run with a fresh workspace.
Crash after patch or revert but before commit

Delete workspace and restart from a fresh verified snapshot.

Do not attempt to reconstruct local state.
Crash after commit but before push

A fresh run can recreate and verify the deterministic commit.

However, Git commit SHA depends on:

tree
parent
author
committer
message
timestamps

To reproduce the same SHA, commit timestamps must be persisted and reused.

Therefore store planned commit metadata before commit creation.
Crash during push

Use remote-query reconciliation before any retry.
42. Deterministic commit plan

Before creating integration or recovery commit, persist a CommitPlan.

Fields:

author timestamp
committer name
committer email
committer timestamp

Then create the commit using:

rather than git commit.

This is more deterministic and avoids worktree-side behavior.

43. Controlled commit creation with git commit-tree

def create_commit_from_plan(
    *,
    git_binary: str,
    repository_path: Path,
    plan,
) -> str:
    env = {
        "PATH": "/usr/bin:/bin",
        "HOME": "/nonexistent",
        "GIT_CONFIG_NOSYSTEM": "1",
        "GIT_AUTHOR_NAME": plan.author_name,
        "GIT_AUTHOR_EMAIL": plan.author_email,
        "GIT_AUTHOR_DATE": plan.author_date,
        "GIT_COMMITTER_NAME": plan.committer_name,
        "GIT_COMMITTER_EMAIL": plan.committer_email,
        "GIT_COMMITTER_DATE": plan.committer_date,
    }

    completed = subprocess.run(
        [
            git_binary,
            "commit-tree",
            plan.tree_sha,
            "-p",
            plan.parent_sha,
        ],
        cwd=repository_path,
        env=env,
        shell=False,
        input=plan.message,
        text=True,
        stdout=subprocess.PIPE,
        stderr=subprocess.PIPE,
        check=False,
        timeout=60,
    )

    if completed.returncode != 0:
        raise CommitCreationFailed(
            sanitize_git_error(completed.stderr)
        )

    return completed.stdout.strip()

This approach should replace the earlier git commit recommendation in P3.4.

It gives stronger reproducibility and recovery semantics.

async def test_reverts_verified_integration_commit(
    api_client,
    recovery_worker,
    seeded_integrated_patch,

    integration = seeded_integrated_patch.integration_attempt

    incident_response = await api_client.post(

            f"/api/v1/integration-attempts/"

            "summary": "Regression detected after integration.",
            "details": (
                "The affected endpoint returns invalid data."
            ),
            "affected_environment": "production",
            "detected_at": "2026-07-31T03:30:00Z",
            "external_reference": "INC-2026-0042",
        },
        headers={
            "Authorization": "Bearer incident-reporter-token"
        },
    )

    assert incident_response.status_code == 201
    incident_id = incident_response.json()["id"]

    assessment_response = await api_client.post(
        (
            f"/api/v1/recovery-incidents/"
            f"{incident_id}/assessments"
        ),
        json={},
        headers={
            "Authorization": "Bearer recovery-assessor-token"
        },
    )

    assert assessment_response.status_code == 201
    assessment = assessment_response.json()

    assert assessment["recommended_strategy"] == "revert_commit"
    assert assessment["direct_revert_possible"] is True

    approval_response = await api_client.post(
        (
            f"/api/v1/recovery-assessments/"
            f"{assessment['id']}/approvals"
        ),
        json={
            "decision": "approved",
            "reason": (
                "The regression is confirmed and "

            ),

        },
    )

    assert approval_response.status_code == 201
