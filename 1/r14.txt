1. Purpose

The Manifest is the only project-specific input required by AI-Enterprise.

A client never describes databases.

A client never describes APIs.

A client never describes microservices.

A client never describes React components.

The client describes the business.

Everything else is inferred.

The Manifest therefore becomes the contract between business intent and software generation.

2. Manifest Definition

A Manifest is a structured document that answers one question:

"What system should AI-Enterprise build?"

It does not answer:

How should it be built?
Which framework should be used?
Which database should be selected?
Which cloud provider should be deployed?
Which programming language should be chosen?

Those are implementation decisions made by AI-Enterprise according to platform policies and generation strategies.

3. Core Principle

Every field in the Manifest must satisfy three rules:

It describes business intent.
It is implementation-independent.
It can be validated automatically.

If a field cannot satisfy all three, it does not belong in the Manifest.

7. Organization

Defines the organization that owns the system.

Example:

{
  "organization": {
    "name": "Acme Hospital",
    "industry": "Healthcare",
    "country": "Germany",
    "size": "Enterprise"
  }
}

Organization information influences policies but never changes business logic.

21. Constraints

Defines mandatory limitations.

Example

Must remain on-premise.

Data cannot leave EU.

Open-source components only.

Use PostgreSQL.

Deploy inside Kubernetes.

Unlike preferences, constraints are mandatory and validated.

22. Deployment Preferences

Preferences guide generation where multiple valid options exist.

Example

Preferred Cloud

Preferred Frontend

Preferred Language

Preferred CI/CD

Preferred Monitoring

Preferences may be overridden only if they violate constraints.

23. Manifest Versioning

Every Manifest contains:

Manifest Version

Schema Version

Registry Version

Generator Version

Compiler Version

This guarantees reproducible builds.

24. Validation Rules

A Manifest is valid only if:

Required sections exist.
Schema matches the current version.
Every referenced object exists in the Registry.
No duplicate identifiers exist.
No circular business dependencies exist.
Constraints are internally consistent.
Policies are compatible.
Workflows reference valid capabilities and entities.

Validation failures stop generation immediately.

This minimal Manifest is sufficient for AI-Enterprise to begin compilation.

27. Manifest Evolution

The Manifest is a living artifact.

Each revision:

receives a new version identifier,
preserves previous versions,
triggers incremental recompilation,
regenerates only impacted artifacts,
updates the execution graph,
maintains full traceability.

No manual synchronization is required.

28. Manifest Contract

The Manifest guarantees that:

Business intent is expressed once.
Technical implementation is never embedded.
Every project starts from the same canonical structure.
Validation occurs before any generation.
All generated artifacts remain traceable to explicit business intent.
The same Manifest, Registry, and generator versions always produce the same logical system.
29. Outcome

With R14 completed, AI-Enterprise now has:

A universal, machine-readable Manifest contract.
A validation target for the bootstrap repository defined in R13.
A stable interface between business stakeholders and the AI-Enterprise compiler.
The foundation for deterministic, repeatable software generation independent of implementation technologies.

R14 completes the input boundary of the platform. The next logical specification, R15, should define the Manifest Compiler—the engine that transforms a validated Manifest into the semantic Knowledge Graph and executable Execution Graph consumed by planners and generators.
