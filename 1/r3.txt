R3 — AI-Enterprise Foundation Implementation Specification
Version

Document: R3
Title: AI-Enterprise Foundation Implementation Specification
Version: 0.1
Status: Implementation Baseline
Depends on: R1 and R2

1. Purpose

R3 defines the first implementation foundation of AI-Enterprise.

R1 defines the MVP vision, scope, architecture, and target workflow.

R2 defines the technical controls required to implement that vision safely and consistently.

R3 converts those decisions into an executable engineering specification.

The objective of R3 is to establish a deterministic, versioned, traceable project-model foundation before introducing AI interpretation, artifact generation, or advanced orchestration.

2. Implementation Objective

The first implementation shall support the following deterministic workflow:

Client Manifest
    ↓
Manifest Parsing
    ↓
AEPM Schema Validation
    ↓
Canonical Object Creation
    ↓
Canonical Relationship Creation
    ↓
Deterministic Validation
    ↓
Validation Findings
    ↓
Human Review State
    ↓
Immutable Project Snapshot

At the completion of R3, the system shall be able to receive a machine-readable client manifest and create a validated, versioned, traceable canonical project model.

R3 does not include AI extraction or document generation.

3. R3 Success Condition

R3 is complete when the system can:

Accept an AEPM v0.1 manifest in JSON or YAML.
Validate the manifest against a formal JSON Schema.
Reject structurally invalid manifests.
Convert a valid manifest into canonical AEIR objects.
Create first-class relationships between objects.
execute deterministic validation rules.
Produce structured validation findings.
Persist the project, objects, relationships, sources, and versions.
Create an immutable project snapshot.
Reconstruct the exact project state from that snapshot.
retain traceability from every canonical object to its source manifest location.
pass automated tests for valid and invalid example projects.

The AI-Enterprise Project Manifest is the authoritative client input for a project.

AEPM v0.1 captures project intent and essential business knowledge without attempting to represent the entire enterprise.

7. AEIR v0.1 Canonical Object Model
7.1 Purpose

AEIR v0.1 is the canonical internal representation created from AEPM.

AEIR shall not preserve the source document structure as its authoritative model.

It shall normalize all project concepts into canonical objects and relationships.

7.4 Status Separation

The system shall maintain three independent status dimensions.

Lifecycle status

Allowed values:

draft
active
deprecated
archived
Truth status

Allowed values:

asserted
inferred
assumed
verified
disputed
Approval status

Allowed values:

not_required
pending
approved
rejected

The system shall not combine these status dimensions into one field.

7.5 Confidence

Confidence shall be represented as a decimal value between 0.0 and 1.0.

Confidence shall not replace truth status or approval status.

Objects directly asserted by a client source may initially receive confidence 1.0, while AI-inferred objects introduced later may receive lower confidence values.

10. Deterministic Validation Rules

R3 shall implement deterministic validation before any AI reasoning.

10.1 Schema Rules
The manifest must conform to AEPM v0.1.
Every identifier must match its object-type prefix.
Every identifier must be unique within a project.
All required fields must be present.
Every enumerated value must be supported.
Dates and timestamps must use ISO 8601.
10.2 Intent Rules
A project must contain at least one intent.
Every intent must contain a name and description.
Every intent must reference a source.
At least one intent must be approved before snapshot approval.
10.3 Outcome Rules
Every outcome must reference or relate to an intent.
Every outcome must define a measurable indicator.
Every outcome metric must contain a target.
Every outcome must have an owner or owning stakeholder relationship.
10.4 Stakeholder Rules
Every project must contain at least one business owner.
Every referenced stakeholder must exist.
Every stakeholder with decision authority must have approval status recorded.
10.5 Capability Rules
Every capability must have an owner.
Every capability must support at least one intent or outcome.
Every critical capability must have at least one requirement.
10.6 Process Rules
Every process must define a trigger.
Every process must define at least one input.
Every process must define at least one output.
Every process must have an owner.
Every process must relate to at least one capability.
10.7 Requirement Rules
Every requirement must have at least one acceptance criterion.
Every requirement must trace to an intent, outcome, capability, process, or rule.
Every critical requirement must be approved before an approved snapshot is created.
Rejected requirements shall not be included in approved snapshots.
10.8 Rule Rules
Every rule must have a defined rule type.
Every rule must have a structured or textual expression.
Every rule must relate to at least one requirement, process, entity, or integration.
10.9 Entity Rules
Every entity must have an owner.
Every entity must have at least one attribute.
Entity attribute names must be unique within the entity.
Every required attribute must define a data type.
10.10 Integration Rules
Every integration must define direction.
Every integration must define exchanged data.
Every integration must define an authentication or security method.
High-criticality integrations must have an associated risk or quality requirement.
10.11 Traceability Rules
Every canonical object must reference at least one source.
Every approved object must be traceable to an approved intent or source assertion.
Every relationship must reference valid objects.
No active object may remain orphaned unless its type explicitly allows it.
10.12 Duplication Rules

The deterministic engine shall detect:

duplicate identifiers
exact duplicate names within the same object type
duplicate active relationships
duplicate source checksums

Semantic similarity detection is excluded from R3 and will later belong to the AI interpretation layer.

11. Project Workflow
11.1 Project States
Created
→ Imported
→ Validation Pending
→ Clarification Required
→ Client Review
→ Approved
→ Ready for Compilation
→ Archived
11.2 Transition Rules
Created to Imported

Allowed when:

a source manifest has been registered
parsing has completed
Imported to Validation Pending

Allowed when:

AEPM schema validation succeeds
canonical objects have been created
Validation Pending to Clarification Required

Required when:

at least one blocking validation finding exists
Validation Pending to Client Review

Allowed when:

no blocking findings exist
Clarification Required to Client Review

Allowed when:

all blocking findings are resolved or explicitly accepted
Client Review to Approved

Allowed when:

required project objects are approved
no unresolved blocking findings remain
a reviewer with decision authority approves the project
Approved to Ready for Compilation

Allowed when:

an immutable approved snapshot has been created successfully
12. Versioning Model
12.1 Object Versioning

Canonical objects shall be immutable by version.

Updating an object shall:

preserve the existing version
create a new version
increment the version number
create an event-log entry
record the actor responsible for the change
12.2 Relationship Versioning

Relationships shall follow the same versioning model as canonical objects.

12.3 Deletion

Canonical objects and relationships shall not be physically deleted through normal application operations.

Removal shall be represented by:

lifecycle status change
validity end date
archival event

Administrative erasure required by law shall be handled by a separate controlled process outside R3.

13. Snapshot Model
13.1 Purpose

A project snapshot is an immutable record of an exact approved project state.

Artifacts introduced in later phases shall compile from snapshots, not from mutable current-state records.

13.2 Snapshot Structure
snapshot_id: "SNP-0001"
project_id: "PRJ-001"

aepm_version: "0.1"
aeir_version: "0.1"

status: "approved"

object_versions:
  - object_id: "INT-001"
    version: 1
  - object_id: "OUT-001"
    version: 1
  - object_id: "REQ-001"
    version: 2

relationship_versions:
  - relationship_id: "REL-001"
    version: 1

validation_summary:
  errors: 0
  warnings: 2
  information: 4
  accepted_risks: 1

created_at: "2026-08-04T19:00:00+02:00"
created_by: "USR-001"
approved_by: "USR-002"
13.3 Snapshot Rules

An approved snapshot shall not be created when:

blocking findings remain open
required approvals are missing
referenced object versions do not exist
referenced relationship versions do not exist
source traceability is incomplete
the project lacks an approved intent

Snapshots shall never be modified after creation.

22. R3 Acceptance Criteria

R3 shall be accepted only when all of the following are true:

AEPM v0.1 has a formal JSON Schema.
AEIR v0.1 has a formal canonical schema.
Relationships are first-class records.
Status dimensions are separated.
Every object has source traceability.
Every update creates an immutable version.
Every meaningful change creates an event.
Deterministic validation executes without AI.
Validation findings are structured and persisted.
Blocking findings prevent approval.
Approved project snapshots are immutable.
Exact snapshot reconstruction is tested.
Valid and invalid example manifests are included.
Automated tests cover all critical rules.
The complete system runs locally in Docker.
No LLM is required for R3 operation.
23. Architectural Invariant

The following invariant governs all R3 implementation decisions:

Every accepted project state must be structurally valid, versioned, reproducible, and traceable to its source.

Any implementation choice that violates this invariant shall be rejected.

24. Transition to R4

R4 may begin only after R3 acceptance.

R4 shall introduce the first AI interpretation capability:

Convert unstructured client manifesto text into candidate AEPM and AEIR objects.

R4 shall preserve all R3 controls.

AI-generated objects shall:

use structured output
pass AEPM and AEIR schema validation
record model and prompt provenance
use truth_status: inferred or truth_status: assumed
use approval_status: pending
require human review
remain traceable to source text
never modify approved project knowledge silently

R3 therefore establishes the trusted deterministic foundation on which AI capabilities can safely operate.

R3 is now the implementation specification for the foundation. The logical next document is R4 — AI Interpretation and Manifest Extraction Specification.
